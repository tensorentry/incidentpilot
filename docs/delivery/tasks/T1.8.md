# T1.8 — Tool envelope and error codes

**Milestone:** M1 Contracts · **Issue:** IP3-002 · **Status:** done

## 1. Understand

- Spec refs: §8.1 tools and trusted context, §8.2 envelope and error codes, D11 in §8.4, §6.6 retry ownership, and invariants 3 and 8 in §3.3.
- Errata: E3 (tool responses return selectors, not strings), E13 (the closed tool set), E16 (`get_trace_summary` is P0).
- The model reads every tool response, so the envelope decides what it can mistake. An empty result could pass for a failed query, partial coverage could pass for a healthy service, and an error could carry an evidence ID that never committed.

## 2. Plan

- **`enums.py`:** `ToolName`, `ToolStatus` and `ToolErrorCode`. Each code knows whether it is retryable.
- **`domain/tools.py`:**
  - `ToolContext`: what the application injects into each call.
  - `ToolError` and `Coverage`.
  - `ToolSource`: the adapter, its version and the snapshot.
  - `ToolResponse`: the envelope itself.

**Acceptance:** each status has one valid shape, and every code maps to a fixed retry decision.

## 3. Validate plan

- **Status rules (§8.2):**
  - `ok`: complete coverage, and it cites the evidence it returned.
  - `empty`: complete coverage, no evidence and no further pages. This is how "nothing there" differs from "couldn't look".
  - `partial`: incomplete coverage. Incomplete coverage never implies the service was healthy.
  - `error`: an error, and no data, coverage or evidence.
- **No evidence ID without a committed row (D11, invariant 3).** An error response can't carry selectors. A stale lease or cancellation (D11's last branch) therefore comes back with no evidence IDs.
- **Retrying is the code's decision, not the adapter's.** Only `TIMEOUT`, `SOURCE_UNAVAILABLE` and `RATE_LIMITED` are retryable. Everything else needs a change first (§6.6). The envelope still has `retryable` as the spec shows, but it must match the code, and only a retryable error may suggest a wait.
- **Trusted context (§8.1).** `ToolContext` holds every value §8.1 keeps from the model that exists in the domain: investigation, attempt, owner, lease epoch and snapshot. Tool arguments are a separate model per tool. Authorization tokens and the budget are never passed per call, because the budget lives on the investigation row.
- **Closed tool set (E13, E16).** The five P0 tools are read from the §8.1 table, not restated in the tests. `search_runbooks` (P1) and `simulate_rollback` (never registered) are rejected.
- **Independent truth.** The error codes, statuses and tools are all parsed from the spec. The spec's sample response parses once E3's changes are applied: a UUID invocation ID, and selectors in place of strings.

**My own choices:**
- the length and count limits: a 500-character message, a 60-second retry hint, 50 gaps, 200 evidence references;
- the cursor pattern, which is opaque URL-safe text;
- `RESULT_TRUNCATED` and `INTERNAL_ERROR` aren't retryable. Repeating the same call won't fix either.

**Corrected along the way:** T1.4's docstring said the model never *sees* a snapshot ID, but the §8.2 envelope shows the model one. The docstring now says the model never *writes* one, which is what §8.1 requires.

**Out of scope:**
- **Each tool's arguments and `data` shape** depend on fixture metrics, so they arrive with T4.3 and T4.4.
- **Sanitizing `message`** is the redaction step in T3.3.
