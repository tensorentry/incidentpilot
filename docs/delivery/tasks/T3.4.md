# T3.4 — Create-incident service with idempotency

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - §7.2 `incidents`: owner, sanitized description, service, severity, requested window, created timestamp, indexed `(owner_id, created_at)`. `idempotency_requests`: owner, operation, key, canonical input hash, resource pointer, unique `(owner_id, operation, key)`.
  - §12.1: `POST /incidents` creates **only** an incident and never starts the agent. The request identity is the normalized body plus the resolved owner plus the operation. The same key and fingerprint return the original resource, and a changed fingerprint returns 409. The key record and the resource are created in the same transaction, under a unique constraint.
  - §3.3 invariant 11: an API retry with the same owner, key and body returns the same resource; the same key with a different body conflicts.
  - §17.1: race claims are verified against real PostgreSQL.
- Errata:
  - **E19:** both tables carry an owner, every unique key includes it, and row-level security is forced.
  - **E10:** the CLI calls this service directly until the HTTP API exists (IP3-010).
- T3.3's sanitizer runs on the description before it's stored.

## 2. Plan

- **`IncidentSeverity`:** `sev1` to `sev4`, worst first. The spec names the field but not a scale.
- **`domain/incident.py`:**
  - `CreateIncident`, the request: a description of 1 to 2,000 characters, a service, a severity and a window of at most 24 hours;
  - `IncidentRecord`, the stored incident with its `sanitizer_version`.
- **Migration `0003`:** `incidents` and `idempotency_requests`, both under owner isolation. The runtime role gets SELECT and INSERT only, and CHECKs mirror the request's rules.
- **Code:**
  - `persistence/incidents.py` and `persistence/idempotency.py`: the SQL.
  - `application/incidents.create_incident(connection, owner, key, request)`:
    1. validates the key and sanitizes the description;
    2. in one owner transaction, claims the key with `INSERT ... ON CONFLICT DO NOTHING`;
    3. either inserts the incident, or compares fingerprints and returns the original or raises `IdempotencyConflict`.

**Acceptance:** concurrent identical requests produce one incident (the plan's acceptance for T3.4); a different request under the same key conflicts; keys belong to their owner.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| Key record and resource in one transaction (§12.1) | Both inserts run in one owner transaction. A rollback leaves neither, and a test shows a waiting request then creates the incident itself |
| Unique constraint decides concurrency (§12.1) | Primary key `(owner_id, operation, key)`. A second claim blocks on the first's uncommitted row, then sees it once committed |
| Fingerprint = normalized body + owner + operation (§12.1) | `sha256_digest` of the operation, owner and validated request, using T1.1's canonical JSON |
| Never starts an investigation (§12.1) | Only `incidents` and `idempotency_requests` are written |
| Sanitized description (§7.2, D04) | `sanitize(limit=2000)` runs before any write. A description with nothing visible is refused. The stored row records `sanitizer_version` (§15.2) |
| Owner isolation (E19) | Both tables are forced under the policy, and the key is scoped to its owner. The catalog checks pass with three tenant tables |
| Rows never change | No UPDATE or DELETE grant on either table |

**Decisions of mine:**
- **The 24-hour bound on the incident window.** The spec bounds only the 2-hour telemetry search window, which applies at investigation start (T3.5).
- **The fingerprint covers the raw request,** not the sanitized description. Sanitizing is deterministic, so both give the same answer, and the raw request is what the caller sent.
- **The `start_investigation` operation is allowed already,** so T3.5 needs no constraint change.

## 5. Validate implementation

**Contention tests are deterministic.** The first transaction claims the key and inserts the incident, then stays open. The second request is started, checked to be still blocked after 0.3 s, and only then is the first transaction committed or rolled back. Three cases:
- **Identical retry:** waits, then returns the first incident with `created = False`.
- **Different request:** waits, then raises `IdempotencyConflict`.
- **First rolls back:** the waiting request creates its own incident, and only that one exists.

A fourth test races five identical requests on five connections: one creates the incident and four return it.

**A test bug of mine:** the five-connection race first entered each connection's context manager and dropped the reference. Python then finalized the abandoned generator, which closed the connection. It now holds them with an `AsyncExitStack`.

**Planted faults in migration `0003`:**

| Fault | Caught by |
|---|---|
| Key unique on `(operation, key)` without the owner | The catalog's unique-key check, and `test_keys_belong_to_their_owner` |
| No owner isolation on `incidents` | The catalog's isolation check, and `test_keys_belong_to_their_owner` |
| Runtime role may UPDATE keys | `test_incidents_and_their_keys_never_change` |

**Mutation testing** found seven survivors on the first run:
- **Six renamed the fingerprint's keys.** Tests only compared fingerprints with each other, but stored fingerprints are compared with new requests across releases, so the exact encoding is a contract. A test now pins one request's fingerprint.
- **One changed the message for a key whose incident is missing.** That branch can't run, because neither table allows DELETE and both rows commit together. It's now an assertion that says why.

## 6. Test

- `make check` passes offline with 1322 unit tests, and 1 skipped because the network test only runs in CI.
- `make test-integration` passes with 79 tests.

**Limits:**
- **No listing yet.** `GET /incidents` with cursor pagination comes with the API (IP3-010). The `(owner_id, created_at)` index is already there for it.
- **Keys are kept forever.** §12.1 asks for at least as long as the resource. Retention and garbage collection (§7.3) come later, and must delete a key together with its resource.
- **A key whose resource is missing raises an error.** That can't happen while neither table allows DELETE.
