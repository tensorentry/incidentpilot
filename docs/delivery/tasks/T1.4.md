# T1.4 — Evidence and selector models

**Milestone:** M1 Contracts · **Issue:** IP3-002 · **Status:** done

## 1. Understand

- Spec refs: §7.4 `EvidenceSelector`, §7.2 `evidence`, §8.2 `evidence_refs`, §8.3 time windows, invariants 3 and 4 in §3.3.
- Errata: E3 (one selector type), E14 (dedup key), E15 (unit of evidence and its four kinds), E19 (owner on every row).
- The spec's selector is a sketch: `kind: str`, plus an arbitrary `path`. Models write selectors, so a loose selector here would let a report cite things nobody can check.

## 2. Plan

- `domain/window.py`: `TimeWindow`, in UTC and half-open.
- `domain/evidence.py`:
  - a selector variant for each E15 kind, joined into one union;
  - `EvidenceRecord`, the row header;
  - `check_selector`, which tests one selector against one row.
- `EvidenceKind` goes in `enums.py`.
- `domain/contract.py` holds the shared base.

**Acceptance:** cross-snapshot and malformed selectors are rejected.

## 3. Validate plan

- **Split with T1.7.** This task checks one selector against one row. T1.7 checks a whole report against an index of visible evidence, including observation IDs and outcome rules.
- **Selectors carry no owner and no snapshot,** because the model never sees either (§8.1). Unknown fields are rejected, so neither can be slipped in, and nor can E15's dropped `path`.
- **Owner before snapshot.** E19 imports a fixture once per owner, so two owners can hold the same snapshot ID. A snapshot check alone would accept another owner's evidence.
- **Every selector field is required.** Optional fields complicate strict structured output, which T1.6 tests.
- **Independent truth:** the kinds are read from the E15 table, not restated in the test.

**Out of scope:**
- Each kind's content shape and the `source_ref` builder belong to T2.1 and T4.2, where fixtures define them. E14's `source_type` column holds the evidence kind. Metric and dependency series share a kind, so `source_ref` has to tell them apart.
- Visibility grants and report-level citation checks are T1.7.

## 5. Validate implementation

**A gap in `make mutate`, fixed.** After the first clean run, I checked which functions `mutmut` had actually mutated. It skips decorated functions, so neither Pydantic validator was touched, and nor were four older functions from T0.3 and T1.1. The first "232/232" said nothing about the window-ordering, window-presence or digest checks.

`make mutate` now mutates decorated functions itself. It flips comparisons, swaps `and` and `or`, drops `not`, swaps conditional branches and negates `if` conditions. To show the check can fail, I ran it in a throwaway copy:

| Change to the tests | Reported |
|---|---|
| None, as a control | Nothing |
| Deleted the equal start and end test | Exactly the `<=` mutation in `_ends_after_start` |

The R1 review record carries a correction, because its coverage claim was wrong.

**Behaviour checked before relying on it:**
- Pydantic keeps a `+01:00` offset as given, so times are converted to UTC explicitly.
- Strict mode accepts JSON strings for UUIDs and times but rejects them from Python, which is the intended boundary.

**Two test expectations I had wrong:** a non-finite float is rejected with the more specific "floats must be finite", and my helper's positional `kind` could be bound by `**fields`, which mypy flagged.

**Limits:**
- **`content` can still be changed in place.** It's a `dict` inside a frozen model, so it can be edited after validation and stop matching its digest. Persistence has to check the digest again on read (T3.11).
- **The selector schema uses `oneOf`.** Some structured-output modes accept only `anyOf`, so T1.6 has to confirm it works, or adjust it.
- **Nothing produces or stores evidence yet.**
