# T3.6 — Fence primitive

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - §3.3 invariant 2: every workflow, evidence, report and event mutation needs a valid current lease epoch.
  - §6.1: under the investigation row lock, a durable write verifies `current_attempt_id`, `lease_epoch`, `status` and `lease_expires_at > db_now`. A stale worker can't commit evidence, tool-call completion, state, the final report or events.
  - §6.5's fenced-commit pseudocode: `SELECT ... FOR UPDATE`, require all four, otherwise roll back with `STALE_LEASE`.
- The plan's acceptance for T3.6: a stale epoch can't commit.
- T3.5 created the columns. Claiming, which sets them, is T3.8, so these tests set them directly.

## 2. Plan

- **`persistence/fence.py`:**
  - `Lease`: owner, investigation, attempt and epoch, which is what a worker holds after a claim.
  - `fenced_transaction(connection, lease)`: an owner transaction that first locks and checks the row, raises `StaleLease` if any check fails, and otherwise yields for the worker's writes.
- **`tests/integration/harness.still_blocked`:** the shared check that a task is still waiting on another transaction's lock. The earlier contention tests now use it too. This is the barrier helper T3.1 deferred to here.

**Acceptance:** a stale epoch, attempt, owner, status or expired lease commits nothing; a reclaim can't take over while a fenced transaction is open.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| Checked under the row lock (§6.1) | `SELECT ... FOR UPDATE` on the investigation, held until commit |
| All four conditions (§6.5) | One SQL expression. A NULL attempt or expiry makes it NULL, which counts as stale |
| Database time, not worker time (§6.1) | `clock_timestamp()`, so a worker's clock can't extend its own lease |
| Nothing written when stale (invariant 2) | The check runs before control returns to the caller, and raising rolls the transaction back |
| Running states only | `RUNNING` and `VALIDATING`. Every other status is refused, which a test covers one by one |
| Owner isolation (E19) | It runs inside `owner_transaction`. Another owner's lease finds no row and is stale |

**On a test clock:** T3.1 deferred barrier and test-clock helpers to here. Expiry uses database time, so tests move `lease_expires_at` relative to `clock_timestamp()` rather than faking a clock. That's deterministic, and it exercises the real comparison.

**A known window:** a lease can expire while a fenced transaction is open. That's safe, because a reclaim needs the row lock and waits until the transaction ends, and the worker learns of the expiry at its next fenced transaction. So fenced transactions must stay short, and the module says so.

## 5. Validate implementation

**A planted fault exposed a gap.** Removing `FOR UPDATE` first went unnoticed: the reclaim test's write appended an event, and appending updates the investigation row, which takes the same lock anyway. Later fenced writes, such as evidence and tool calls, won't touch that row. A new test opens a fenced transaction that writes nothing and shows a reclaim still waits; it fails without `FOR UPDATE`.

**Planted faults:**

| Fault | Caught by |
|---|---|
| No `FOR UPDATE` | `test_the_fence_itself_holds_the_row_until_commit` (added after this probe) |
| Expiry ignored | `test_an_expired_lease_cannot_commit` |
| Status ignored | All five `test_an_investigation_that_isnt_running_takes_no_writes` cases |
| Epoch ignored | The older-epoch and newer-epoch cases |

**The acceptance scenario:** an old worker holds an open fenced transaction; a reclaim is shown to be blocked, then completes once the old transaction commits; the old worker's next write raises `StaleLease`, and the new worker's succeeds.

**Mutation testing:** `fenced_transaction` is a decorated function, so mutmut skips it and the harness's decorated-function step covers its comparison and condition. Nothing survived.
