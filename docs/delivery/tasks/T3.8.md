# T3.8 — Attempts, capacity slots and the claim transaction

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - §6.1 claim transaction: select queue work with `FOR UPDATE SKIP LOCKED`, then lock one free capacity slot. Allocate the attempt, increment `lease_epoch`, set the lease owner and expiry by database time, advance to `RUNNING`, and append `ATTEMPT_STARTED`, all in one transaction committed before external calls.
  - §6.1 capacity: database-backed slots enforce at most two concurrent investigations installation-wide. Lock order: investigation row first, then capacity slot. With no slot free, roll back and retry later.
  - §6.5: "no `LIMIT 1` accidental selection mismatch", with races verified on real PostgreSQL.
  - §2.4: 2 active investigations; a 180 s deadline from first claim. §3.2: recovery never resets the deadline.
  - §7.2: `attempts`, unique `(investigation_id, attempt_no)`; `capacity_slots`, a pre-created bounded set, unique bound attempt.
- Errata:
  - **E8:** workers claim only investigations in their own mode.
  - **E19:** claim selection, slot binding and slot release are three of the five scheduler functions. They return IDs only; binding and release check the attempt belongs to the current owner. The runtime role has no direct grants on `capacity_slots`. The claim selects across owners, then the rest of the same transaction runs under that owner.
- The plan's acceptance for T3.8: two workers contend, and at most two are ever active.

## 2. Plan

- **Migration `0005`:**
  - `attempts`, under owner isolation, keyed `(owner_id, id)`, with unique `(owner_id, investigation_id, attempt_no)` and a composite foreign key to the investigation. Every final status has an end time.
  - `capacity_slots`: two pre-created rows, no owner column, no runtime grants, and a CHECK that a slot's binding fields are all set or all empty.
  - Three scheduler functions:
    - `claimable_investigation(mode)`: `FOR UPDATE SKIP LOCKED`, oldest first, filtered by mode and eligibility; returns `(owner_id, investigation_id)`;
    - `bind_capacity_slot(attempt, epoch)`: checks the attempt's owner, then takes a free slot with `SKIP LOCKED`; returns the slot or NULL;
    - `release_capacity_slot(attempt)`: frees the current owner's slot; returns whether one was bound.
- **`persistence/database.py`:** `scheduler_transaction`, a transaction that starts with no owner, and `adopt_owner`, which sets the owner once inside it.
- **`workflows/claim.claim_next(connection, worker_id, mode)`:** returns a `Lease` or None.

**Acceptance:** concurrent workers never hold more than two slots; a locked investigation or slot is skipped, not waited for; another owner's work is claimed under that owner.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| Lock order: investigation, then slot (§6.1) | The selection function locks the investigation, then the binding function locks a slot, in that order inside one transaction |
| `SKIP LOCKED` for both (§6.1) | Two deterministic tests hold an investigation, or a slot, in an open claim and show another claim proceeds within 5 s |
| Roll back when no slot (§6.1) | The attempt insert comes first, so the binding can check its owner. A NULL slot raises inside the transaction, so the attempt and every other change roll back. A test shows the third investigation stays `QUEUED` with no attempt |
| At most two active (§2.4) | Two slots. Three rounds of five concurrent workers over four queued investigations each bind exactly two |
| Mode filter (E8) | A live investigation isn't claimed by an offline worker, and is by a live one |
| Cross-owner selection, then one owner (E19) | `scheduler_transaction` starts ownerless and sees no tenant rows; `adopt_owner` then fixes the claimed row's owner and refuses a second owner |
| IDs and counts only (E19) | Each function's return type is checked against an allowlist, with EXECUTE for the runtime role only |
| Binding checks the owner (E19) | Binding another owner's attempt raises; releasing it returns false and leaves the slot bound |
| Deadline from first claim, kept on recovery (§2.4, §3.2) | `coalesce(deadline_at, now + deadline)`. A recovered claim keeps the original deadline and gets epoch 2 and attempt 2 |
| Committed before external calls (§6.1) | `claim_next` returns only after its transaction commits |

**Decisions of mine:**
- Ties on `created_at` are broken by ID, so selection order is total.
- `claimable_investigation` returns only `QUEUED` and `RETRY_WAIT` rows whose `eligible_at` has passed. The limit on recovery attempts is enforced by the sweeper in T3.10, which moves exhausted work to `FAILED` instead of `RETRY_WAIT`.

## 5. Validate implementation

**Planted faults in migration `0005`:**

| Fault | Caught by |
|---|---|
| Investigation selected with `FOR UPDATE`, not `SKIP LOCKED` | `test_a_locked_investigation_is_skipped_not_waited_for` |
| No mode filter | `test_a_worker_claims_only_its_own_mode` |
| Binding ignores the attempt's owner | `test_a_slot_cannot_be_bound_for_another_owners_attempt` |
| Three slots | Seven tests, including all three contention rounds |
| Eligibility time ignored | `test_a_retry_is_claimed_once_eligible_and_keeps_its_deadline` |
| Slot selected with `FOR UPDATE`, not `SKIP LOCKED` | Nothing at first: the outcome stays right because a blocked claimer re-checks and moves on. `test_a_slot_held_by_an_open_claim_is_skipped_not_waited_for` now catches it |

**A probe that didn't run:** my first batch of probes printed nothing, because macOS has no `timeout` command. They were rerun without it before anything was concluded from them.

**Mutation testing** found one survivor: computing the new epoch from `attempts_started` instead of `lease_epoch`. Every test kept the two equal, but they're different counters, and the epoch is a fencing token that must only increase. A test now advances the epoch on its own and checks the next claim builds on it.
