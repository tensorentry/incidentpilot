# T1.7 — Cross-record validators and citation checker

**Milestone:** M1 Contracts · **Issue:** IP3-002 · **Status:** done

## 1. Understand

- Spec refs: §10.1 report sections, §10.2 structural checks, §9.4 fallbacks, and invariants 4 and 9 in §3.3.
- Errata:
  - **E3:** records above observations cite observation IDs, which must resolve inside the report.
  - **E4:** the rules for each outcome, and a floor for `high` confidence.
  - **E6:** these checks are structural, and never a claim that the evidence supports the cause.
  - **E19:** evidence belongs to an owner.
- T1.5 left out everything that needs more than one record. Without this task, an abstention could still name a root cause.

## 2. Plan

`domain/report_checks.py` has three functions, each returning every issue it finds:
- `candidate_issues`: repeated IDs, references that don't resolve, and E4's outcome rules.
- `citation_issues`: every selector in the candidate, checked against an index of the evidence this investigation can see. This covers observation references, measurement inputs, and both terms of a ratio.
- `report_issues`: both checks above, plus the rules for application-written reports. The snapshot comes from the report's identity, and the owner from the caller.

The "fake evidence index" is a plain mapping from evidence ID to row. In T3.11 the database provides it.

**Acceptance:** causes in an abstention are rejected.

## 3. Validate plan

- **Every issue at once.** D13 allows one bounded repair. Reporting only the first error would waste it on one problem when there are three. A test checks that a candidate with three problems gets three issues.
- **Issues name a place, not a value.** A path like `observations[1].references[0]` and a fixed message are enough to repair from. Messages never repeat cited values or evidence content.
- **Invariant 4.** Every selector goes through T1.4's `check_selector`, so owner, snapshot, kind and window are checked in one place. A row missing from the index is "can't see", which is how invisible evidence looks to the checker.
- **Trusted inputs.** The owner is passed in by the caller, from the investigation. The snapshot comes from the report's identity, which the application writes. Neither comes from the model.
- **E4's rules as written:**
  - a diagnosis needs a root cause, and each accepted cause needs `medium` or `high` confidence;
  - a partial diagnosis needs a supported hypothesis;
  - an abstention accepts no root cause;
  - a partial diagnosis or an abstention states its limitations.

**Three readings of my own:**
- **Every accepted cause needs a supporting observation, whatever the outcome.** E4 says this only for `diagnosed`. A partial diagnosis that accepts an unsupported cause would be an unsupported causal claim, which §9.4 forbids.
- **"Two supports citing different evidence IDs" means the two supports cite different sets of evidence.** Two observations built on the same rows corroborate nothing.
- **An application-written report holds no hypotheses and no alternatives, and it abstains.** Invariant 9 forbids it manufacturing causes, and weighing alternatives is causal reasoning too. A model-written abstention may still list what it tested, as E4 allows.

**Out of scope:**
- **`component` being in the authorized service graph.** This needs the snapshot's graph, which arrives with T2.1 and T3.2.
- **Whether a value matches its inputs.** That's the numeric stage, in M5.
- **Wiring into publication.** That's T4.9.

## 5. Validate implementation

**Mutation testing found one gap.** When a root cause names an unknown hypothesis, the loop skips it with `continue`. Changing that to `break` would silently skip every root cause after it, and no test noticed. A new test puts an unknown cause before a faulty one and expects both issues.

Most tests compare the full list of issues, so an extra or missing issue fails the test, not only a wrong one.
