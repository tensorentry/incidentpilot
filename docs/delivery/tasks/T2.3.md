# T2.3 — Second and third contrasting cases

**Milestone:** M2 Fixtures · **Issue:** IP3-003 · **Status:** done

## 1. Understand

- Spec refs: §14.1, whose table lists the three causally contrasting MVP cases.
  - `case-4K8`: checkout latency, an unrelated deploy, and a payments dependency that really is degrading. Expected: reject the coincidence and find the dependency.
  - `case-9J1`: checkout latency with missing or lagged dependency telemetry. Expected: abstain, or a partial report that names the missing test.
- §14.1 also asks for unrelated deploys in positive cases and for no-deploy faults. Case 2 is both.
- The three cases have to contrast causally while looking the same from outside, or the investigator could tell them apart by surface details instead of telemetry.

## 2. Plan

- **Restructure `evaluation/cases.py`.** All three cases share one incident report, service graph and set of nine series. Each case supplies a `Behaviour` (how each series moves), its logs, deploys and spans.
- **Telemetry builders can leave gaps.** `counts` and `latencies` take a `present` test. A missing minute gets no point, rather than a zero.
- **Two new cases:** `dependency_degradation` and `missing_dependency_telemetry`.
- **Tests:** a new `test_cases.py` holds the signal tests for all three cases. `test_generator.py` keeps reproducibility and file writing.

**Acceptance:** each case carries the signals §14.1 describes, and the committed files match a fresh run.

## 3. Validate plan

- **Case 2 rejects the coincidence.**
  - A harmless checkout deploy (an email template) lands four minutes before payments starts degrading, with no payments deploy at all.
  - Tests check that payments' own latency doubles and its errors rise tenfold, and that checkout's wait on payments rises at least threefold in the traces.
  - Inventory stays flat, and checkout's call volume doesn't change.
- **Case 3 can't be decided.**
  - Checkout slows after a deploy that touches every outbound call, an HTTP client upgrade.
  - All six downstream series have no points in the incident window, but full points in the baseline window.
  - There's no incident-window trace summary, and a log line explains that the downstream exporter fell behind.
  - The oracle has no causes and accepts only an abstention or a partial report.
- **The cases look alike from outside.** A test checks that the three manifests are identical apart from the snapshot ID: same summary, windows and graph.
- **Case 1 didn't change.** After the restructure, its committed file was byte-for-byte the same, so the refactor preserved every random draw in order.

**My own choices:**
- the magnitudes and timings of each fault;
- in case 3, losing telemetry five minutes before checkout slows, so no visible data points at the cause.

## 5. Validate implementation

**Mutation testing found dead code that pretended to be ground truth.** Case 3 originally set inventory to slow down at minute 70, while downstream telemetry stopped at minute 65. Those values never reached any file, so changing them changed nothing: four equivalent survivors. Worse, the docstring claimed "inventory is in fact slow", which nothing in the fixture supports.

I removed the values and changed the docstring to say the fixture records no cause. The bytes are unchanged by construction, because the generator draws nothing for missing minutes.
