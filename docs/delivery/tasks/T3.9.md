# T3.9 — Worker loop and lease renewal

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - §6.1 lease parameters: a 30-second lease, renewed every 10 seconds. "The worker stops new dispatch if renewal fails." Long-running calls are cancellable on a best-effort basis, but an external provider may finish and bill after ownership is lost.
  - D08: a worker claims, renews, and loses its lease to a reclaim. A stale worker can't commit.
- The plan's T3.9 also hosts the sweeper. The sweeper's logic is T3.10, so this task gives the loop a maintenance hook between claims.
- T3.6's fence and T3.8's claim are the pieces this loop drives.

## 2. Plan

- **`workflows/lease.py`:**
  - `renew_lease(connection, lease, duration)`: a fenced UPDATE that moves `lease_expires_at` to `duration` from database now. A stale lease raises `StaleLease` and changes nothing.
  - `LeaseKeeper`: renews every `every` on its own connection until stopped, and sets `lost` when a renewal fails. `require()` raises `StaleLease` once lost; a job calls it before each dispatch.
- **`workflows/worker.py`:** `Worker(worker_id, mode, job, maintenance, lease_duration, renew_every, poll_interval)`:
  - `run_once(connection, keeper_connection)`: claims one investigation in the worker's mode, runs `job(connection, lease, keeper)` while the keeper renews, then stops the keeper. It returns False when there's nothing to claim.
  - `run(connection, keeper_connection, stop)`: maintenance, then `run_once`, waiting `poll_interval` when idle, until `stop` is set.

**Acceptance:** a kept lease outlives its first expiry; a lost lease stops dispatch within one renewal interval; a failing job doesn't stop the worker.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| 30 s lease, renewed every 10 s (§6.1) | The defaults. A keeper refuses an interval that isn't shorter than the lease |
| Renewal is fenced | `renew_lease` writes inside `fenced_transaction`, so a stolen lease can't be extended |
| Stop dispatch when renewal fails (§6.1) | `lost` is set and `require()` raises. A test steals the lease mid-job, and the job sees `StaleLease` before dispatching |
| Renewal never collides with the job's transactions | The keeper uses a second connection |
| No cancellation mid-renewal | The keeper is stopped by an event it checks between renewals, never by cancelling a task during a query |
| Database lost counts as lease lost | Any `psycopg.Error` during renewal sets `lost` too |
| A failing job doesn't stop the worker | `run_once` logs the exception and returns. The lease lapses, and T3.10's sweeper will close the attempt |

## 5. Validate implementation

**Timing.** These tests shorten the lease to 1 s and renewal to 0.2 s, leaving 0.8 s of slack. A control test shows an unkept 1-second lease lapses after 1.2 s. Because the tests depend on time, I ran the whole integration suite 24 times, four processes at once, the load mutation testing creates, and all runs passed.

**Mutation testing found 15 gaps,** all in the new tests rather than the code:
- **Durations not passed through:** dropping the worker's or keeper's lease duration silently used the 30-second default. Tests now check the claimed and renewed expiry is within the short duration.
- **Log lines unchecked:** nothing verified that a failed job or a lost lease is logged with its investigation, which an operator needs. Both messages, and the failed job's exception, are now asserted.
- **Maintenance connection unchecked:** the maintenance hook's connection was never used. The test's maintenance now runs a query on it.
- **Idle-wait logic:** an inverted idle check or a wait that never times out survived. One test now counts exactly one maintenance pass while idle, so the worker doesn't spin. Another adds work while the loop idles, and it must be picked up.
- **Keeper connection never used:** no job ran long enough for the keeper to renew. The loop test's jobs now outlast a renewal interval.

The parallel run was repeated after these changes: 16 more four-way runs all passed.

**Limits:**
- **A failed job leaves its attempt `RUNNING` and its slot bound until the lease expires.** Closing the attempt and releasing the slot is T3.10's `close_attempt`, which the worker will call.
- **There's no worker process yet.** The loop is a library. A `worker` entry point arrives with the scripted fake model (T3.11), which gives it a job to run, and the kill/restart demo (T3.13) runs two of them.
- **Losing the database connection ends `run`.** Reconnecting with backoff belongs with the worker process.
