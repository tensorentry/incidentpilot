# T3.7 — CLI over application services

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Errata:
  - **E10:** Phase 1 needs a CLI before the HTTP API exists, so the CLI calls application services directly until IP3-010, then moves to HTTP.
  - **E19:** the CLI takes an owner, defaulting to the local one.
- Spec refs: D03 prefers "a low-dependency CLI before enabling the UI"; §12.1 for the operations it mirrors.
- The services exist: import snapshots (T3.2), create an incident (T3.4) and start an investigation (T3.5).

## 2. Plan

- **`src/incidentpilot/cli.py`,** installed as the `incidentpilot` command. Each command prints JSON:
  - `import-snapshots [--root DIR]`;
  - `create-incident --service --severity --start --end --description [--key]`;
  - `start-investigation INCIDENT --snapshot --start --end [--mode] [--key]`. The mode defaults to the process mode; another mode is refused by the service (E8);
  - `show-investigation ID`: state, frozen configuration and events.
- A global `--owner`, defaulting to the local owner.
- **Idempotency:** without `--key`, a fresh key is generated and printed, so a retry can reuse it.
- **Requests** are validated through JSON, as the API will. Errors name fields and messages, never input values.
- **The snapshot module** keeps only the import service; its standalone `main` is gone, so there's one command surface. `make import-snapshots` now runs `incidentpilot import-snapshots`.
- **`persistence/events.list_events`** for `show-investigation`.

**Acceptance:** the whole Phase 1 path, import, report, start and show, works from the command line against PostgreSQL, for a named owner.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| Calls services directly (E10) | `execute` calls the same functions the API will, with no logic of its own beyond formatting |
| Owner from the caller, defaulting to local (E19) | `--owner`, defaulting to `LOCAL_OWNER_ID`. Another owner's investigation reports as not found |
| Mode can't be switched per request (E8) | The process mode comes from settings, and `--mode` only states the request's mode, which the service compares |
| Errors don't leak input | Validation errors list field paths and messages only. A unit test plants a canary in the description |
| Retry-safe | Same key, same request: the original resource, with `created: false` |

**Deviation from §16.4's layout:** the spec places the CLI at `apps/cli/main.py`. It lives at `src/incidentpilot/cli.py` with a console-script entry point, so it's packaged, importable by tests, and installed by `uv sync`. `apps/` can hold thin launchers once the API and worker processes exist.

## 5. Validate implementation

**Run by hand against the real `incidentpilot` database:** `make migrate`, `make import-snapshots`, then `incidentpilot create-incident`, `start-investigation` and `show-investigation`. The investigation showed `QUEUED` with one `INVESTIGATION_QUEUED` event.

**Test fixes of mine:**
- argparse rewraps help text, so the help test compares with whitespace collapsed.
- Parsed JSON in the integration tests is typed `Any`, replacing scattered `type: ignore` comments.

**Mutation testing found 79 gaps,** all in the CLI's own surface:
- making a required option optional;
- dropping a choice list;
- changing help text or the program name;
- leaving `idempotency_key` out of the start command's output, or renaming an event's `payload` or `at`;
- changing the JSON's indentation or key sorting;
- changing how validation errors join field paths and problems.

The CLI is an interface people and scripts depend on, so these are now tested as a contract:
- every required option is required;
- an unknown mode is a usage error;
- help names the program, each command's summary and each explained option, with whole lines pinned rather than substrings;
- output is sorted, indented JSON;
- validation errors read `field.path: message; ...`.
