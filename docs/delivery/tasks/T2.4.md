# T2.4 — Non-leakage test

**Milestone:** M2 Fixtures · **Issue:** IP3-003 · **Status:** done

## 1. Understand

- Spec refs:
  - §14.4: the worker must never import oracle code or know causal labels, enforced by module boundaries and explicit non-leakage tests.
  - §14.1: case names, fixture paths and model-visible metadata must not reveal the cause.
  - IP3-003's acceptance in §16.3: no oracle metadata in investigator input.
- T2.1 already blocks the code path: no worker module can import `incidentpilot.evaluation`. This task covers the data path, meaning everything under `scenarios/observations/` that a worker mounts.

## 2. Plan

- **`evaluation/leakage.py`:** `forbidden_terms` and `leaks`.
  - The forbidden terms are the case's family name in three spellings, every cause category in two spellings, the oracle's discriminating tests, and answer words such as "oracle" and "root cause".
- **`write_case` refuses to write** a bundle that contains any forbidden term. It writes neither file.
- **`GeneratedCase.family`:** each case records its family name, so its terms can be built.
- **`tests/unit/evaluation/test_non_leakage.py`:** checks the committed files as a worker would read them.

**Acceptance:** nothing an investigator can see carries any case's answer.

## 3. Validate plan

- **Two lines of defence.**
  - The generator can't write a leaking case.
  - The tests read the committed files directly, so a file edited by hand is caught too.
- **Any case's answer is forbidden in every bundle,** not only its own. The spec's example case IDs (`case-7Q2` and the others) are forbidden as well.
- **Nothing else is visible.** The observations folder holds only bundles named `snap-` plus 12 hex digits, and one README. Each bundle parses with unknown fields rejected, so no file can carry an oracle section. Each has an oracle file kept in the other folder, and no bundle mentions `scenarios/oracle`.
- **Unanswerable cases are covered too.** Case 3 has no causes, but its family name and tests are still forbidden.

## 5. Validate implementation

**The committed-file test can fail.** I temporarily wrote "Root cause found in payments" into a committed bundle. Exactly two tests failed: the non-leakage test for that file, and the drift test. Then I restored the file from git.

**The guard can fail.** Tests plant four forms of a term into a generated case:
- `dependency_degradation`
- `resource saturation`
- `Root cause`
- `dependency-degradation`

Each time, `write_case` raises and writes nothing. A case that mentions only telemetry still writes.

**One test bug of mine:** I assumed the README sorted last, but uppercase sorts first. Bundles and the README are now listed separately.

**Mutation testing** found one survivor, the comma separating terms in the error message, because every test planted a single term. One test now plants two terms and matches the full message.

## 6. Test

`make check` passes with 1006 tests, and 1 skipped because the network test only runs in CI.

**Limits:**
- **Text matching catches labels, not implications.** A deploy note like "Check stock for each cart item…" legitimately hints at case 1's mechanism, as a real change record would. Whether data gives an answer away too easily is a question of benchmark design, judged on live runs in T4.10 and M6.
- **The repository is public, which can contaminate the benchmark.** A model trained on this repository could learn which snapshot ID is which case, without reading any telemetry. These three cases are fine for development. M6's challenge cases have to be generated with fresh seeds and kept out of the public repository until they're run. This matches §14.1's advice to retire studied challenge sets.
- **What the model is actually sent isn't checked yet.** The briefing and prompt get their own leakage check when T4.6 builds them.
