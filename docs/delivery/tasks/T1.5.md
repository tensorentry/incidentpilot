# T1.5 — Report candidate, published report and measurement models

**Milestone:** M1 Contracts · **Issue:** IP3-002 · **Status:** done

## 1. Understand

- Spec refs: §7.4 contracts, §9.1 `CandidateOrStop`, §9.4 fallbacks, §10.1 report sections, §10.2 validation stages, §10.3 sample, invariants 6, 8 and 9 in §3.3.
- Errata:
  - **E2:** quantities live in a typed `Measurement`, never in prose.
  - **E3:** observations and measurements cite selectors, while everything above them cites observation IDs.
  - **E4:** `root_causes` lists accepted `cause_id`s.
  - **E5:** the model writes a `ReportCandidate`, and the application wraps it in a `DiagnosisReport`.
  - **E6:** a published report says `semantic: not_assessed`, and a stage that never ran says `not_run`.
- §7.4 is a sketch: free-text kinds, roles and confidence, and no measurement. The model writes the candidate, so every loose field here is something it can get wrong without anyone noticing.

## 2. Plan

- **`domain/measurement.py`:** `Measurement` and `Quantity`, a ratio's numerator or denominator.
- **`domain/report.py`:**
  - the candidate's records: observation, hypothesis, alternative, recommendation and impact;
  - `ReportCandidate`, plus `Stop` and the `CandidateOrStop` alias that joins them;
  - `DiagnosisReport`, with application-written identity, execution and validation sections.
- **`enums.py`:** nine new vocabularies.

**Acceptance:** unknown fields are rejected.

## 3. Validate plan

- **Split with T1.7.** Each record here checks itself and nothing else. These checks need more than one record, so they belong to T1.7:
  - cited observation and cause IDs resolve;
  - IDs don't repeat across records;
  - E4's rules per outcome, and its floor for `high` confidence;
  - invariant 9, and the rule that an application-written report is an abstention.

  For example, an `insufficient_evidence` candidate with a root cause is well formed here, and T1.7 rejects it.
- **The model can't write identity, execution or validation fields (E5, §8.1).** They exist only on `DiagnosisReport`, and a test reads E5's lists to confirm that. A recommendation has no `requires_approval` field, because approval is the application's call (invariant 8).
- **No quantities in prose (E2).** Every free-text field the model writes rejects a number followed by a unit or `%`. Numbers inside names (`v2`, `p95`) and numbers without units (`HTTP 503`) are allowed, as E2 says.
- **A published report can't overclaim (E6, ADR-006):**
  - `structural` must be `passed`;
  - `numeric` must be `passed` or `not_run`;
  - `semantic` must be `not_assessed`.
- **Measurements stay recomputable.**
  - A series input has to select exactly the window measured.
  - A ratio carries both terms and the inputs behind them.
  - A ratio covers its numerator's window, so it can compare an incident window with a baseline window.
- **Execution is consistent:**
  - Only the investigator finishing publishes a model-written candidate. Every other reason publishes an application-written one.
  - A cancelled investigation never publishes. Cancellation and completion are serialized, and the winner is final (invariant 7).
- **Strict structured output (for T1.6).** Every field is required and unknown fields are forbidden. "Absent" is written as `null`, never by leaving a field out. A test walks the generated schema to check this.
- **Independent truth.** These values are read from the spec or errata, not restated in the tests:
  - the claim kinds, roles, confidence levels and alternative statuses;
  - the candidate's field list;
  - the fields E5 moves out of the candidate.

  The spec's sample hypothesis parses unchanged.

**My own choices, not taken from the spec:**
- the aggregation and unit lists;
- the identifier patterns;
- the length limits: 500 characters of text, 20 items per list, 50 observations;
- dropping `percent` in favour of `ratio`, so there is one way to write a proportion.

These are easy to widen later, and T1.6 tests them against a real model.

**Out of scope:**
- **Cost in the usage summary.** It needs the pricing table and the full ledger, both in M5.
- **Coverage on a measurement.** The application derives it from evidence; the model doesn't write it.

## 5. Validate implementation

**First run green, then checked why.** All 653 domain tests passed on the first run, so I checked that each rejection test fails for the reason it names:
- **Quantity check.** In a throwaway copy, I turned it off. Exactly the 10 prose fields in a full candidate then accepted "40%". The other 41 strings (IDs, enum values, times) still rejected it.
- **Bare `ValidationError` tests.** For each, I printed where the rejection happened. All 52 cases fail at the field they target, such as `component: string_pattern_mismatch` or `validation.semantic: literal_error`.

**One wrong assumption.** I first built test inputs with plain strings for enum values. Strict mode rejects those from Python and accepts them only from JSON. The model's output arrives as JSON, so the tests now validate through JSON. A separate round-trip test covers construction from Python.

**Five survivors on the first mutation run.** Each was an error message wrapped in `XX…XX`. The tests matched only part of the message, so they still passed. They now match the whole message.

## 6. Test

`make check` passes with 690 tests, and 1 skipped because the network test only runs in CI.

`make mutate` catches every mutation (§5).

**Limits:**
- **The quantity rule is a pattern, not understanding.**
  - It misses counts without a unit, such as "240 requests", and numbers written as words.
  - It rejects "HTTP 503s", reading the `s` as seconds.
  - T1.6 shows how often a real model hits either case.
- **The spec's sample observation would be rejected.** It uses the old flat selector, and makes a computed claim with no measurement. Both are what E2 and E3 changed.
- **The schema uses `oneOf`** for selectors, as T1.4 noted. T1.6 confirms strict structured output accepts it.
- **Nothing yet checks that a value matches its inputs.** That is the numeric stage, in M5.
