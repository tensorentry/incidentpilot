# T2.1 — Fixture schema, snapshot manifest and oracle boundary

**Milestone:** M2 Fixtures · **Issue:** IP3-003 · **Status:** done

## 1. Understand

- Spec refs: §14.1 to §14.4 scenarios and the oracle-isolated pipeline (D17), §16.4 layout, D03 read-only fixture mount, and §8.3 telemetry semantics.
- Errata:
  - **E7:** a snapshot registry, filled by an import step from `scenarios/observations`.
  - **E12:** the generator lives in `evaluation/`, an import contract keeps worker code out of it, and workers mount only observations.
  - **E15:** the unit of evidence, which fixture records must be able to produce.
- The boundary goes in before any oracle data exists, so no case can ever have been written on the wrong side of it.

## 2. Plan

- **`domain/names.py`:** the service, category, metric and local-ID types, moved out of the report and measurement modules so snapshot code doesn't import report code.
- **`domain/snapshot.py`:** `ServiceGraph`, `Incident` and `SnapshotManifest`.
- **`adapters/fixture_bundle.py`:** `ObservationBundle` and its records, plus `bundle_sha256`, which gives the snapshot's `content_sha256`. The records are metric series (scalar or histogram, optionally for a dependency), log records, deployments and span summaries.
- **`evaluation/oracle.py`:** `Oracle` and `OracleCause`, the answer for one case.
- **`scenarios/observations/` and `scenarios/oracle/`:** a README each, explaining the boundary.
- **`tests/unit/test_oracle_boundary.py`:** the import contract.

**Acceptance:** the build fails if worker code can reach oracle code.

## 3. Validate plan

- **How the boundary is enforced.** `make check` runs a test that parses every module outside `evaluation/` and flags three things:
  - any import that resolves to `incidentpilot.evaluation`, in any form (absolute, relative, `from incidentpilot import evaluation`, or inside a function);
  - any string mentioning the package, which catches `importlib.import_module`;
  - any string mentioning `scenarios/oracle`, which catches file paths.

  Docstrings are exempt because they never run. I wrote this check rather than add `import-linter`: it needs no new dependency, and it also catches string references, which import graphs miss.
- **The check can fail.** A test plants `from ..evaluation.oracle import Oracle` in a copy of the source tree, and the check names that file. Ten import forms are each caught, and five look-alikes (such as `evaluations_archive`) aren't flagged.
- **E7.** The manifest carries what the `snapshots` table needs: ID, adapter version, nullable parent and service graph. `bundle_sha256` gives the content digest. It ignores JSON key order and time-zone offsets, and it changes when any content changes.
- **The service graph bounds scope (§8.3).** Every record's service has to be in the graph, and every dependency has to be an edge in it, in the direction of the call. `allows(caller, callee)` is what the gateway will use.
- **Coverage can be measured honestly (§8.3).**
  - Series points sit on a fixed time grid, in order. A missing point is a visible gap rather than something hidden.
  - Latency is stored as histograms, because raw percentiles can't be averaged.
  - Every point in a histogram uses the same bucket bounds, so they can be aggregated.
- **E15 units are present.** Each series, log record, deployment and span summary is one future evidence row. A series names its `dependency`, so metric rows and dependency rows stay distinct.
- **Oracle rules.**
  - An unanswerable case can't accept a diagnosis.
  - An answerable case can't accept an abstention, which counts as a miss (§14.3).

**My own choices:**
- `observation_window` and `incident` in the manifest, which E7 didn't list;
- histogram buckets that aren't cumulative, plus an overflow count;
- the size limits.

**Left open:** the category vocabulary. Reports and oracles share one category pattern, and grading will compare categories exactly. The actual set of categories gets fixed with the cases, in T2.2 and T2.3.

**Out of scope:**
- the generator (T2.2);
- the import step and table (T3.2);
- the read-only container mount (T3.1);
- the adapter that turns records into evidence rows, and `source_ref` (T4.2).

## 5. Validate implementation

**The first draft of the boundary check would have failed `main`.** It flagged docstrings that only mention the boundary, such as the one in `adapters/__init__.py`. It now skips docstrings, and a test confirms that a docstring passes while a real string constant is still caught. I also had one relative-import expectation backwards in my own test: from inside the `adapters` package, `from .. import evaluation` does reach the evaluation package.

**Rejections checked.** For each bare `ValidationError` case, I printed where it was rejected. All 29 fail at the field they target.

**Mutation testing:** three survivors on the first run, all error messages that the tests matched only in part. They now match the whole message.

## 6. Test

`make check` passes with 939 tests, and 1 skipped because the network test only runs in CI.

**Limits:**
- **The boundary check reads source code, not runtime behaviour.** It can't see an import built from pieces at runtime, such as `"incidentpilot." + "eval" + "uation"`. The second line of defence is the container mount in T3.1, where workers never receive `scenarios/oracle`.
- **No bundle or oracle data exists yet.** T2.2 generates the first case.
- **The incident summary and record text can still leak an answer.** Whether they do is T2.4's non-leakage test.
