# T3.12 — Atomic terminal publication

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - §6.5: one atomic terminal transaction inserts the investigation's unique report, sets `COMPLETED`, closes the attempt, releases capacity and appends an event.
  - §6.4 D09: cancellation and finalization take the same row lock. Whichever commits first wins, and the other sees the final state.
  - Invariant 1: one current attempt, one published report and one terminal outcome per investigation.
  - §7.2: `report_candidates` (attempt, content hash, schema) and `diagnosis_reports` (unique investigation, published report, validator version, publish time).
  - §10.1: the report's identity matches the frozen request, and its execution section is written by the application.
  - IP3-004 exit: two workers contend, a stale report commit fails, and there is one final report.
- Errata:
  - **E1:** the candidate commits in the same fenced transaction as `RUNNING → VALIDATING`. A recovery attempt validates the stored candidate with no new model or tool calls. `repair_requests_used` survives recovery.
  - **E5:** the model writes only `ReportCandidate`; `DiagnosisReport` wraps it with application-written identity, execution and validation.
  - **E6:** each stage reports its own status. `numeric: not_run` until the numeric validator exists, and `semantic: not_assessed` always.
  - **E9:** publication closes the attempt through `close_attempt`.
  - **E17:** fallbacks pass through `VALIDATING` too.

## 2. Plan

- **Migration `0008`:**
  - `report_candidates`: insert-only, with the author, termination reason, prompt digest and content digest. CHECKs tie the author to the reason and exclude `cancelled`.
  - `diagnosis_reports`: insert-only, one per investigation (`UNIQUE (owner_id, investigation_id)`), with the outcome, report JSON, digest and validator version.
  - Two CHECKs on `investigations`: `termination_reason` comes from the enum, and it is set exactly when the status is terminal.
- **`workflows/publication.py`:**
  - `submit_candidate` stores the candidate and moves `RUNNING → VALIDATING`, appending `VALIDATION_STARTED`.
  - `resume_validation` (E1) finds the newest stored candidate and moves `RUNNING → VALIDATING` with it, or returns `None`.
  - `publish_report` runs one transaction:
    - builds the `DiagnosisReport` from the investigation's own rows;
    - runs the structural checks against the evidence the investigation can see;
    - inserts the report and closes the attempt as `SUCCEEDED`;
    - ends the investigation `COMPLETED` with `REPORT_PUBLISHED`.

  All three run inside the caller's fenced transaction.
- **`domain/report.check_authorship`:** the author-and-reason rule, shared by the `ReportExecution` validator and `submit_candidate`.
- **`ScriptedModel`:**
  - after the script it hands in a candidate, by default an abstention citing every record it saw, then publishes it;
  - a recovery attempt resumes a stored candidate instead of replaying the script;
  - a new fault, `CRASH_BEFORE_PUBLISH`, strikes between the two.

**Acceptance:** one report under contention; a stale or cancelled worker can't publish; cancel and publish race to exactly one terminal outcome; a worker lost during validation is recovered by publishing its candidate, with no new calls.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| One published report per investigation (invariant 1) | A unique key on the investigation. A second publication from the same lease fails the fence, because the investigation is `COMPLETED`, and a direct second insert fails the key |
| Publication is atomic (§6.5) | Report, attempt, slot, status and event change in one fenced transaction. A failed check raises before any write |
| Cancel and publish race to one outcome (D09) | Both take the investigation row lock. Tests queue each one first in turn and check the single outcome |
| A stale worker can't publish (§6.1) | `publish_report` runs inside `fenced_transaction`. A test has the lost worker's late publication refused after recovery |
| Candidate commits with `RUNNING → VALIDATING` (E1) | Same transaction in `submit_candidate` |
| Recovery validates the stored candidate without new calls (E1) | `resume_validation`. A test checks the counters don't move between the crash and the publication |
| Model writes no identity, execution or validation (E5) | The report is assembled from the investigation row, the ledger counters and the candidate row |
| No false validation claims (E6) | `numeric: not_run`, `semantic: not_assessed` |
| Report cites only visible, snapshot-matched evidence (invariant 4) | `report_issues` runs against `visible_evidence` before insertion |
| Only a finished investigator's candidate is the model's (§9.4) | `check_authorship` before writing, and a CHECK in the schema |
| Ended investigations give a reason | A CHECK that `termination_reason` is set exactly when the status is terminal |

**Deviations and decisions:**
- **The structural validator is the T1.7 checker, run at publication.** A report that fails it raises `ReportRejected` and publishes nothing, leaving the investigation `VALIDATING`. Repair and the `FAILED` path come with the validator stage (T4.9).
- **The report's usage is read before the attempt closes its open calls.** A call still in flight at publication becomes `UNKNOWN` afterwards, so it isn't counted in the report. Only the scripted model can leave one in flight; a runner settles its calls before it hands in a candidate.
- **`tool_calls_completed` is 0** until the gateway adds tool calls (T4.3).
- **The scripted model's prompt digest is a fixed stand-in,** `SCRIPT_PROMPT_SHA256`, since it has no prompt. The runner records the real prompt digest (T4.7).
- **`REPORT_PUBLISHED` carries the report's ID and digest** beside the reason, so a stream reader can fetch it.
- **A recovery attempt resumes the newest candidate.** Only a repair (T4.9) can store a second one.
- **The candidate keeps the attempt that wrote it, and the report the attempt that published it.**

## 5. Validate implementation

**Planted faults.** Mutation testing doesn't reach module-level SQL or migrations, so 18 faults were planted one at a time:
- each filter and ordering in the candidate lookups;
- the validation status write and its row version;
- the status check behind a candidate;
- the investigation columns a report is built from;
- each new constraint, grant and row-security policy.

All 18 were caught. Two needed new tests first: one for the newest of two candidates, and one for another investigation's candidate. A third caught only once a test checked the row version.

**Other findings:**
- **The catalog vocabulary check didn't match a CHECK that combined two rules,** so the candidates' "not cancelled" rule became its own constraint.
- **Older tests set ended statuses without a reason,** which the new CHECK refuses. They now give one from a shared `ENDED_BECAUSE` table.
- **`bound_slots` moved to `seeding.py`,** so the publication tests share it without importing another test module.

**Mutation testing** found 11 survivors on the first run, all in the scripted model's default ending:
- **The abstention's text and numbering:** its claim, its limitation and the observation numbers starting at 1 went unchecked, because the integration tests only counted observations.
- **The window on a series citation:** no script commits a metric series, so dropping or misnaming the window never ran.

A new unit test pins `cite` for both selector shapes and the whole abstention.

After the fix:

| Target | Result |
|---|---|
| `mutmut` | 3921/3921 killed |
| State edges | 124/124 caught |
| Enum values | 145/145 caught |
| Decorated functions | 164/164 caught |

The author-and-reason rule moved from a Pydantic validator into the plain function `check_authorship`, so mutmut now covers it, and the decorated-function count fell from 170 to 164.

## 6. Test

- `make check` passes offline with 1419 unit tests, and 1 skipped because the network test only runs in CI. Of these, 3 are new, for the scripted model's default ending.
- `make test-integration` passes with 308 tests. Of these, 36 are new:
  - 30 for publication;
  - 2 for the scripted model: a crash during validation, and the crash planted before publishing;
  - 4 for the new vocabularies in the catalog check.

**Limits:**
- **A rejected report stays `VALIDATING`.** Its job raises, the lease lapses, and recovery retries the same candidate until attempts run out. Repair, and failing at once with `no_admissible_report`, come with T4.9.
- **A lease renewal that lands just after publication logs a lost lease.** The investigation is no longer running, so the renewal fails. Publication itself is unaffected.
- **A budget-stopped script still hands in nothing.** The fallback report is T4.8.
