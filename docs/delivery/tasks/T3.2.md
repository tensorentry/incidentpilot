# T3.2 — Snapshot table and import step

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Errata:
  - **E7:** a `snapshots` table with `id`, `content_sha256`, `service_graph`, `adapter_version`, a nullable `parent_snapshot_id` and `created_at`. Rows are immutable. An explicit import step fills it from `scenarios/observations`, and the API reads only the table.
  - **E19:** snapshots belong to an owner and are keyed `(owner_id, id)`. The import step imports a fixture for a named owner, so the same fixture imported for two owners becomes two snapshots. Every unique key includes the owner, and a reference to a parent stays inside one owner.
  - **E12:** the import step reads only `scenarios/observations`.
- ADR-005 (immutable snapshots) and ADR-014 (owner isolation).
- The registry holds the manifest and the bundle's digest, not the telemetry itself. Workers read telemetry from the read-only fixture mount (D03), and the digest lets the fixture adapter (T4.2) check that a file hasn't changed since import.

## 2. Plan

- **Migration `0002`:** the `snapshots` table, under `owner_isolation`. The runtime role gets SELECT and INSERT only.
- **`persistence/snapshots.py`:**
  - `insert_snapshot` stores a snapshot for the transaction's owner. It returns False if the same content is already there, and refuses the same ID with different content.
  - `get_snapshot` reads one back as a `SnapshotManifest`.
- **`application/snapshots.py`:** the import step, `python -m incidentpilot.application.snapshots [--owner UUID] [--root DIR]`, also run by `make import-snapshots`. The owner defaults to the local one (E19's change to E10). Each file must be a valid bundle named after its snapshot.

**Acceptance:** each owner sees only its own snapshots, a snapshot never changes once imported, and the committed fixtures read back exactly.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| Rows are immutable (E7, ADR-005) | No UPDATE or DELETE grant. Re-importing different content is refused, not overwritten |
| Keyed `(owner_id, id)` (E19) | Primary key. A catalog test now checks that every unique key on a tenant table includes `owner_id` |
| A parent stays inside one owner (E19) | Composite foreign key `(owner_id, parent_snapshot_id)`. A test proves owner B can't descend from owner A's snapshot |
| Not its own parent | A CHECK, because the foreign key alone would accept a row that references itself |
| Forced row-level security (E19) | `owner_isolation("snapshots")`. The T3.1 catalog test now checks a real table |
| Import for a named owner (E19) | `--owner`, defaulting to the local owner |
| The API reads only the table (E7) | `get_snapshot` rebuilds the full manifest from the row |

**One deviation from E7:** the service graph isn't a column of its own. The whole manifest is stored as JSONB, holding the graph, the incident and the observation window. The columns that keys and constraints need (`id`, `parent_snapshot_id`, `adapter_version`) are copied out of it, and a CHECK keeps the copies equal to the manifest. Reading a row back gives the exact manifest that was imported, which a test checks for each committed fixture.

**Parents import first.** A missing parent is reported by name. The import step doesn't order files by ancestry, because no fixture has a parent yet; that arrives with the simulator in P1.

## 5. Validate implementation

**A test bug of mine:** the self-parent case named another fixture's ID as the parent, so it hit the foreign key instead of the CHECK. It now uses the row's own ID.

**Planted faults in migration `0002`:**

| Fault | Caught by |
|---|---|
| No owner isolation on `snapshots` | The catalog test and four snapshot tests |
| Runtime role granted UPDATE and DELETE | Both `test_snapshots_never_change` cases |
| A unique key on `id` without the owner | The new catalog test, and `test_each_owner_gets_its_own_copy` |

The CHECK constraints are tested directly: each disagreement between a column and the manifest, and a self-parent, is rejected by name.

**A concurrent import of one file on two connections** stores one row: one import reports it created the row, the other that it was already there. The unique key and `ON CONFLICT DO NOTHING` decide it, so the result doesn't depend on timing.

**Mutation testing** found seven survivors on the first run:
- Four changed the import command's help text, which nothing tested. The help now comes from the module docstring, and a test checks it.
- **Two dropped the UUID type on `--owner`, a real gap:** a malformed owner would have reached the database instead of being refused when the arguments were parsed. A test now checks that `--owner everyone` exits with a usage error before anything connects.
- One lower-cased `get_snapshot`'s query. That's equivalent, because SQL keywords aren't case-sensitive. The query is now a module constant, as in `database.py`.

## 6. Test

- `make check` passes offline with 1027 unit tests, and 1 skipped because the network test only runs in CI.
- `make test-integration` passes with 55 tests.
- Against the real `incidentpilot` database, `make migrate` then `make import-snapshots` imported all three fixtures, and a second import reported each as already imported.

**Limits:**
- **Each migration bumps the expected head in `test_migrations.py`.** That's deliberate: a migration that doesn't apply would fail there, rather than pass by matching whatever head exists.
- **The digest isn't checked against files at read time yet.** That's the fixture adapter's job in T4.2.
- **There's no command to list or remove snapshots.** None is needed until the CLI (T3.7), and removal would break immutability.
