# T3.5 — Start-investigation, event append and admission lock

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - §12.1: `POST /incidents/{id}/investigations` is the only start contract. It freezes the snapshot, scope and config, queues the work, and is idempotent.
  - §12.2: the server validates incident ownership, time window, snapshot, service graph, mode configuration and admission capacity, and "validation failures do not create queued work".
  - §2.4: the limits (15 tool calls, 6 per tool, 10 model requests, 2 recovery attempts, a 180 s deadline, a 15 s finalization reserve, an estimated $0.50 spend cap), a 2-hour search window, and a queue of 20.
  - §7.2: the `investigations` and `run_events` columns. §7.3: every mutation appends its event in the same transaction, with `seq` taken from the locked investigation's `next_event_seq`, and the runtime role can't change events.
- Errata:
  - **E8:** frozen values in typed columns, not only a digest. The request's mode must equal the process's mode, and `replay` never creates an investigation.
  - **E11:** after the idempotency check, take `pg_advisory_xact_lock` on a fixed key, then count and insert. Only `QUEUED` counts toward the 20.
  - **E19:** the queue of 20 is installation-wide, so the admission count must see every owner, through a `SECURITY DEFINER` function that returns only a count. Composite foreign keys keep an investigation inside its owner.
  - **E1:** `repair_requests_used` with `CHECK (<= 1)` lives on the investigation.

## 2. Plan

- **`domain/investigation.py`:** `InvestigationLimits` (the §2.4 defaults), `StartInvestigation` (the §12.2 request, with a window of at most 2 hours), `FrozenConfig` with its `digest`, and `InvestigationRecord`.
- **Migration `0004`:**
  - `investigations`: frozen configuration columns, the lease and counter columns later tasks need, and `next_event_seq`, with three composite foreign keys (incident, snapshot, parent).
  - `run_events`.
  - `queued_investigation_count()`, the first scheduler function.
- **Code:**
  - `persistence/events.append_event`: takes the next sequence number with `UPDATE ... RETURNING` on the investigation row, then inserts the event. Payloads are sanitized there.
  - `persistence/investigations.py`: insert, and a read that checks the stored values still match the digest.
  - `application/investigations.start_investigation`: key check, then mode check, then, in one owner transaction:
    1. claim or replay the key;
    2. validate the incident, snapshot, service and window;
    3. take the admission lock and count;
    4. insert the investigation and its `INVESTIGATION_QUEUED` event.
  - `application/idempotent.py` and `application/errors.py`: shared with `create_incident`, which now uses them.

**Acceptance:** concurrent starts never exceed the queue of 20 across owners; a failed validation leaves no row; events are numbered without gaps or collisions.

## 3. Validate plan

| Rule | How it holds |
|---|---|
| Validation failures create nothing (§12.2) | Validation runs inside the transaction that claimed the key, so a failure rolls the claim back too. Four cases leave zero investigations, events and keys |
| Mode equals process mode; `replay` never starts (E8) | `admitted_mode` runs before the database is touched. A test covers every combination |
| Frozen values stored (E8) | Typed columns, plus `config_sha256`. Reading an investigation whose stored values no longer match its digest raises |
| Lock after the idempotency check, then count and insert (E11) | Claim, validate, `pg_advisory_xact_lock`, count, insert, all in one transaction |
| Only `QUEUED` counts (E11) | The function counts `status = 'QUEUED'`. A test moves one row to `RETRY_WAIT` and admits another |
| The count sees every owner and returns only a count (E19) | A `SECURITY DEFINER` function owned by the scheduler role, with a pinned `search_path`, a `bigint` result, and EXECUTE for the runtime role only |
| `seq` from the locked row (§7.3) | `UPDATE investigations SET next_event_seq = next_event_seq + 1 ... RETURNING`, which takes the row lock until commit |
| Events immutable (§7.3) | SELECT and INSERT only |
| Payloads sanitized (§15.1) | Every string goes through `sanitize`, and keys must be snake_case |
| Cross-owner references impossible (E19) | Composite foreign keys for incident, snapshot and parent. A test proves an UPDATE to another owner's incident is rejected |

**The scheduler role, a detail E19 leaves open.** A definer function owned by the migrator would still be limited to the caller's owner, because the policy is forced on the table owner too. So the init script creates `incidentpilot_scheduler`:
- it can't log in, and it has `BYPASSRLS`;
- it may read only the `status` column of `investigations`;
- the migrator can create functions as it (`SET ROLE`) but doesn't inherit its bypass;
- `connect_runtime` now also refuses any role that is a member of a superuser or bypassing role.

**Decisions of mine:**
- The allowed services are the snapshot's whole service graph, sorted.
- The investigation window must lie inside the snapshot's observation window.
- The spend cap is stored in micro-dollars, so no float reaches the ledger.
- Lease, deadline, attempt and repair columns exist now with defaults, so T3.6 to T3.10 add behaviour, not columns.

## 5. Validate implementation

**A real hole: anyone could call the scheduler function.** The migration's `REVOKE ... FROM PUBLIC` and `GRANT ... TO incidentpilot_runtime` ran as the migrator, but the scheduler role owns the function. PostgreSQL silently ignores a revoke by a non-owner, so `PUBLIC` kept its default EXECUTE: every role that could connect could call a function that bypasses row security. The runtime role's own grant had failed too; it could call the function only through `PUBLIC`. The test that inspects every scheduler function's ACL caught it. The privilege statements now run as the owning role.

**Admission is tested deterministically.** With 19 queued, one transaction takes the admission lock and inserts the twentieth without committing. A second start is shown to be blocked on the lock after 0.3 s, then rejected once the first commits. A second test races three starts against two free places: exactly two are admitted.

**Planted faults:**

| Fault | Caught by |
|---|---|
| No admission lock | Both admission race tests |
| Counting this owner's queue only, through row-level security | `test_the_queue_limit_counts_every_owner` |
| Counting every status, not only `QUEUED` | `test_only_queued_work_counts_toward_the_limit` |
| UPDATE granted on events | `test_events_never_change` |

**The stored vocabularies match the enums.** A catalog test reads each CHECK list (incident severity, investigation status, mode, event type) from the database and compares it with the Python enum, so renaming a value in one place fails the build.

**Mutation testing** found 20 survivors on the first run:
- **Twelve in reading an investigation back.** Every test stored the default limits, with no parent and no attempt, so a dropped field or a flipped `None` check went unnoticed. A round-trip test now stores non-default limits, a parent, an attempt, an epoch and a sequence number.
- **Two left the owner or incident out of the stored fingerprint,** which hid a real case: the same key reused for another incident must conflict, not replay. Tests now check that case and that the stored fingerprint is exactly the documented one.
- **Three flipped the case of short SQL strings,** which is equivalent; they're module constants now.
- **Two remained, and both were equivalent:** `NewType` is the identity function at runtime, so `None if x is None else AttemptId(x)` behaves exactly like `AttemptId(x)`. The column values now pass straight to the strict model.

**A mutation run aborted once, because its baseline failed.** Rerunning would have hidden that, so I ran the full suite 20 times with four processes in parallel, the load mutation testing creates, until it was clean. That found four problems in the test harness, not in product code:
- **The sweep test used fixed database names,** so parallel runs collided, and two sweeps could race. The test now uses unique names and checks only what's left. The sweep uses `DROP ... IF EXISTS` and skips a database still in use.
- **The template fingerprint walked the package recursively** while other processes created and removed `__pycache__` folders in it. A folder vanishing mid-walk left an unclosed iterator, which `filterwarnings = error` turned into a crash. It now lists the three known folders.
- **Dropping a copy raced the server-side exit of a just-closed connection.** The migrator may not terminate another role's process, so teardown now retries for up to 5 s.
- **Concurrent pytest runs shared one temporary root** and pruned each other's folders. `tests/conftest.py` now gives each run its own root and removes it afterwards.

After these fixes, 32 parallel full runs all passed.

## 6. Test

- `make check` passes offline with 1356 unit tests, and 1 skipped because the network test only runs in CI.
- `make test-integration` passes with 112 tests.
- The full suite passed 32 times running four processes in parallel.

**Limits:**
- **Nothing claims the queue yet.** Claiming, leases and capacity slots are T3.8. The queue-age limit of 10 minutes is enforced by the sweeper in T3.10.
- **Starting doesn't check an incident's own window against the investigation window,** only the snapshot's coverage. The spec doesn't say whether they must overlap.
- **Parent investigations (reruns) are in the schema but not in the request yet.** Nothing creates a rerun until the CLI and API do.
- **The integrity check runs on read only.** The runtime role may UPDATE investigations, because state changes are UPDATEs, so a changed configuration is detected when read, not prevented. Workers always read through `get_investigation`.
