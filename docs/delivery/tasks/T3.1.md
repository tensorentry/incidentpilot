# T3.1 — PostgreSQL, migrations, roles and the two-owner harness

**Milestone:** M3 Durable slice · **Issue:** IP3-004 · **Status:** done

## 1. Understand

- Spec refs:
  - D03 (§4.2): migrations run as a one-shot job, images are pinned, containers run as non-root, PostgreSQL publishes no port, and credentials stay outside the repository.
  - §7.2's schema policy: UUIDs, `timestamptz`, CHECK constraints and foreign keys. §7.3: the runtime role lacks UPDATE and DELETE on evidence and events where practical.
  - §17.1: real PostgreSQL for every state invariant, never SQLite.
- Errata:
  - **E10:** a dev-only Compose override publishes PostgreSQL on loopback, and a migration seeds one local owner.
  - **E19:** forced row-level security on every tenant table, using `NULLIF(current_setting('app.owner_id', true), '')::uuid`. The owner is set with `SET LOCAL` through one helper. Runtime roles are never superuser, `BYPASSRLS` or table owner, and migrations run as a separate role. The test database always has two owners.
- ADRs: ADR-003 (PostgreSQL queue) and ADR-014 (owner isolation in PostgreSQL).
- **No tenant table exists until T3.2,** so this task proves isolation on a scratch table built with the same helper every tenant migration will use.

## 2. Plan

- **Compose:**
  - `docker-compose.yml`: PostgreSQL 18.7, pinned by digest. It runs as the image's `postgres` user with a read-only root filesystem, no capabilities and `no-new-privileges`, on an internal network with no published port.
  - `docker-compose.dev.yml` publishes it on `127.0.0.1` only (E10).
  - `infra/postgres/initdb/10-roles.sh` creates the database and the two roles when the volume is first created.
- **Roles:**
  - `incidentpilot_migrator` owns the database and schema, and may create databases so the test harness can copy them.
  - `incidentpilot_runtime` owns nothing. It's created with `NOSUPERUSER NOBYPASSRLS NOINHERIT` and can only connect.
- **Migration `0001`:**
  - closes the schema to `PUBLIC`, and grants usage to the runtime role only;
  - revokes the default `EXECUTE` on new functions, so a later `SECURITY DEFINER` function is callable only once it's granted;
  - adds `current_owner_id()`, and the `owners` table seeded with the local owner, which the runtime role can read but not change.
- **Code:**
  - `persistence/isolation.py`: `owner_isolation(table)`, the three statements that enable, force and define the policy, plus the role and owner constants.
  - `persistence/database.py`:
    - `connect_runtime` refuses a role that is superuser, has `BYPASSRLS`, or owns the database or any table in the schema.
    - `owner_transaction` sets the owner for one transaction, and refuses to start inside another transaction, where the owner would outlive the block.
  - `persistence/migrate.py` and `migrations/`: Alembic running hand-written SQL, forward-only.
  - Settings gain `INCIDENTPILOT_DATABASE_URL` and `INCIDENTPILOT_MIGRATION_DATABASE_URL`, both secrets.
- **Harness:** `tests/integration/`. The migrations run once into a template database seeded with a second owner, and each test gets its own copy.
- **Make and CI:**
  - `make infra-up`, `infra-down`, `migrate` and `test-integration`; `make test` now runs unit tests only.
  - A new CI job, `integration`, starts the project's own Compose files with throwaway passwords, migrates and runs the integration tests.

**Acceptance:** owner A can't read or write owner B's rows, a transaction with no owner sees nothing, and the runtime role can't escape either.

## 3. Validate plan

| Rule (E19 unless noted) | How it holds |
|---|---|
| Row-level security enabled **and forced** | `owner_isolation` emits both. Forcing holds the migrator too, which a test checks |
| An unset owner fails closed, including the `''` left after a transaction | `NULLIF` in `current_owner_id()`. Tests cover a fresh connection, after a commit and after a rollback |
| Owner set with `SET LOCAL` through one helper | `owner_transaction` uses `set_config(..., true)` and refuses nesting or a non-autocommit connection |
| Runtime never superuser, `BYPASSRLS` or owner | Role attributes, a test that it owns nothing, and a check in `connect_runtime` |
| Migrations run as a separate role | `make migrate` uses the migrator's connection string. The app never does |
| Definer functions need explicit grants | Default `EXECUTE` revoked, and a test proves a new function is uncallable |
| The test database has two owners | Seeded into the template |
| Off published ports (D03) | Internal network by default; loopback only in the dev override |
| Non-root, pinned images (D03) | `user: 70:70`, read-only root filesystem, digest pin |

**Decisions of mine, recorded in [ADR-015](../../adr/ADR-015-hand-written-sql-forward-only-migrations.md):**
- psycopg 3 with async connections and hand-written SQL, and no ORM;
- forward-only migrations;
- a database per test, copied from a template.

**Moved out of this task:**
- The barrier and test-clock helpers the plan listed go to T3.6 and T3.8, where the first race tests need them. Built now, they'd have nothing to test against.
- The full catalog check stays in T3.14. A first version is here: every table except `owners` and `alembic_version` must have a non-null `owner_id`, forced row-level security and exactly the one policy. It holds trivially until T3.2 adds the first tenant table.

## 5. Validate implementation

**The harness leaked the database password.** The first failing test printed the connection strings, passwords included, because the fixture's dataclass showed them in its repr. They're now excluded from the repr. CI masks its throwaway passwords as well.

**Other fixes:**
- PostgreSQL appends the offending statement to some error messages, so whole-message matches allow trailing lines.
- `make migrate` without configuration printed a traceback. It now exits with the reason.
- The healthcheck goes over TCP. During first-run setup the server listens only on its socket, so a socket check would report ready before the roles exist.

**Planted faults in the SQL,** which mutation testing doesn't cover:

| Fault | Caught by |
|---|---|
| `NULLIF` removed from `current_owner_id()` | Both tests that the owner ends with its transaction |
| New functions executable by default | `test_a_new_function_needs_an_explicit_grant` |
| Schema left open to `PUBLIC` | `test_other_roles_cannot_see_the_schema` |
| `FORCE` removed | `test_the_table_owner_is_held_too` |
| `WITH CHECK` removed | Nothing, correctly: without it PostgreSQL applies `USING` to writes too. It stays, to state the rule |

Each probe also showed that the template database rebuilds when the persistence code changes.

**Mutation testing left seven test databases behind.** Some mutation runs end their test process before fixture teardown, so those copies were never dropped, and each run would have added more. I haven't confirmed which mutmut path does it. Each test run now names its copies after the server process of an admin connection it holds open for the whole run. At start-up, under the template lock, the harness drops any copy whose process is gone. A live run's copies are never touched, and a test proves a stale copy is dropped while live ones survive. The seven leftovers went on the next run.

**Mutation testing** also found one survivor: changing `"script_location"` to `"SCRIPT_LOCATION"` is equivalent, because Alembic reads option names in any case. The name is now a module constant, and the test shares the same config builder.

| Target | Result |
|---|---|
| `mutmut` | 1684/1684 killed |
| State edges | 124/124 caught |
| Enum values | 141/141 caught |
| Decorated functions | 164/164 caught, including `owner_transaction`'s guard |

Migrations are excluded from `mutmut` ([ADR-015](../../adr/ADR-015-hand-written-sql-forward-only-migrations.md)), so the planted faults above stand in for them.

## 6. Test

- `make check` passes offline with 1021 unit tests, and 1 skipped because the network test only runs in CI.
- `make test-integration` passes with 34 tests against PostgreSQL 18.7 from the project's Compose files.
- `make migrate` ran twice against the real `incidentpilot` database: the second run changed nothing, and the runtime role reads the seeded local owner.
- Copying the template takes a median of 10 ms.

**Limits:**
- **Row-level security catches a missed filter, not hostile code.** The runtime role can set any owner. Real authentication comes with IP3-010.
- **`connect_runtime` is only tested against the migrator,** which it refuses because the migrator owns the database. The superuser and `BYPASSRLS` paths aren't exercised, because the harness deliberately has no such role.
- **One runtime role serves the API, workers and CLI.** Separate roles could narrow each one's grants later.
- **The `integration` CI job isn't a required check yet.** Branch protection requires only `check`, and adding it is a repository setting for you to change.
- **`make mutate` now needs the database running and configured,** because mutation runs include the integration tests.
