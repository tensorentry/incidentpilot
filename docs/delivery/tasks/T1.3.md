# T1.3 — Reservation ledger transitions

**Milestone:** M1 Contracts · **Issue:** IP3-002 · **Status:** done

## 1. Understand

- Spec refs: §11.1 and D14 (ledger), D08 and D11 (dispatch order), §6.3 (crash matrix), §6.6 (retry ownership), §7.2 (`model_calls`, `tool_calls`), invariant 5 in §3.3.
- Errata: E9 (closing an attempt), E13 (per-tool quota).
- The ledger is what keeps a crash from hiding spend. A wrong edge here either loses budget or lets a late response rewrite history.

## 2. Plan

Add to `src/incidentpilot/domain/transitions.py`, tests first:

- Model-call and tool-call tables, using the same checks as T1.2.
- An effect function for each, saying what a change does to the reservation.
- The close rule from E9.

Add both tables to `make mutate`.

## 3. Validate plan

The spec had three gaps, so validation added erratum **E18**, accepted 2026-11-08:

- **Tool calls had no state.** E9 says sent calls keep their quota, but the only status on `tool_calls` comes from the tool's answer, which doesn't exist yet for exactly the calls E9 has to close. E18 adds `tool_calls.state`.
- **§11.1 omits `RESERVED → FAILED`.** E9 requires it.
- **A failure after dispatch had no rule.** §11.1 only allows a release if the provider was certainly not contacted, so `DISPATCHED → FAILED` keeps the reservation. Repeated rate-limit errors can therefore stop a run early, which is the safe direction.

Other checks:

- **Independent truth:** tests read edges and effects from the E18 table, and a test ties that table to the §11.1 chain, so the code can't confirm itself.
- **Effects are functions, not tables.** `mutmut` skips module-level tables but mutates function bodies, so this needed no new harness code.
- **Retries:** a physical tool retry stays on its row, and a provider retry is a new row, so neither needs a state.

**Out of scope:**
- Counter arithmetic and cap checks run in SQL under the row lock, so they belong to T4.5 and IP3-008.
- `close_attempt` itself is T3.10. This task only supplies its rule for a single call.
- `TOOL_CALL_UNKNOWN` isn't added. The row records the state, and whether it also needs an event belongs to the event-mapping work in T3.5.

## 5. Validate implementation

**A design gap, recorded in E18.** `FAILED` means two things: `RESERVED → FAILED` released the budget, while `DISPATCHED → FAILED` kept it. The rows look the same afterwards, so the counters couldn't be recomputed from them. E18 adds `dispatched_at` to both tables. No mutation could have found this, because the code is consistent with itself.

**Mutation results,** from a green baseline:

| Target | Mutations | Result |
|---|---|---|
| `make mutate`: function logic | 206 | All killed |
| `make mutate`: state edges | 124 | All caught |
| `make mutate`: enum values | 69 | All caught |
| Hand-written, see below | 18 | All caught by the expected test |

`mutmut` never swaps one enum member for another, and that's the worst mistake here, such as releasing a reservation that should be kept. The 18 hand-written mutations cover that:

- A post-dispatch failure that releases, and `UNKNOWN` settling at zero.
- Each wrong close result.
- Each removed type guard.
- An effect function that skips the legality check.
- The tool check reading the model table.
- The E18 table drifting from the code.

The throwaway script flagged two of these as problems. That was its own mistake: it searched test names for "close", but those tests are named `test_closing_…`. Both mutations failed in the expected tests.

**Limits:**
- Nothing calls these rules yet. M3 and M4 have to use them, and T3.11 has to add `state` and `dispatched_at` to the tables.
- These checks can't show that `DISPATCHED` commits before the request is sent. That ordering needs a crash test against real PostgreSQL, in T3.11 and M5.
