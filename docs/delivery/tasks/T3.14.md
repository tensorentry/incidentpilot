# T3.14 — Cross-owner isolation suite and catalog check

**Milestone:** M3 Durable slice · **Erratum:** E19 · **Status:** done

## 1. Understand

- Spec refs:
  - E19 invariant 9: no row belonging to one owner can be read, cited or written in another owner's context, and PostgreSQL enforces it.
  - E19 testing, which requires:
    - every tenant table refuses another owner's reads, changes and inserts, and a transaction with no owner sees nothing;
    - composite foreign keys reject cross-owner references;
    - a worker can't cite another owner's evidence;
    - scheduler functions return only scheduling fields;
    - a catalog check fails the build if any table, unique index, role or definer function breaks the rules.
  - ADR-014.
- Already in place:
  - **T3.1:** the `owner_isolation` helper, tested on a scratch table. The first catalog check covered the owner column, forced row security and a policy named `owner_isolation`.
  - **Each later task:** cross-owner tests for its own tables, including incidents, investigations, events, snapshots, evidence and reports.
  - **T3.8 and T3.10:** the scheduler function checks.
- Gaps:
  - **The policy's expression went unchecked,** so a table could have a policy named `owner_isolation` that let every row through.
  - **Foreign keys weren't checked,** neither for carrying the owner nor for naming a real owner.
  - **The definer check only looked at functions the scheduler owns.** A definer function owned by anyone else would have been missed.
  - **Grants, other schemas and views weren't checked.**
  - **No single suite tried every operation on every table** with two owners' real rows.

## 2. Plan

- **`test_catalog.py`** gains six checks:
  1. Each policy covers every command and role, permissive, with `(owner_id = current_owner_id())` for both reads and writes.
  2. `current_owner_id()` reads only `app.owner_id`. It is `STABLE`, not a definer, and owned by the migrator.
  3. Every foreign key between tenant tables starts `(owner_id, …) → (owner_id, id)`, and every tenant table references `owners`.
  4. The runtime holds no `TRUNCATE`, `REFERENCES` or `TRIGGER`, at table or column level.
  5. Nothing is granted to `PUBLIC`.
  6. No schema exists but `public`, and every view uses `security_invoker` (no materialized views).
- **`test_scheduler.py`:**
  - the definer check now covers every `SECURITY DEFINER` function, whoever owns it;
  - the scheduler owns no tables.
- **`test_cross_owner.py`:** both owners run a full investigation to a published report, so all 11 tenant tables hold real rows for each. Then, for every table:
  - each owner reads only its own rows;
  - with no owner, nothing is read;
  - another owner's rows can't be changed or deleted;
  - no row can be added for another owner;
  - no row can be given away.

  It also checks that a visibility grant can't join B's evidence to A's investigation, and that a report citing B's real evidence IDs is rejected.

**Acceptance:** each check fails when a matching fault is planted in the schema.

## 3. Validate plan

| E19 requirement | Where |
|---|---|
| Every tenant table refuses another owner's reads, changes and inserts; no owner sees nothing | `test_cross_owner.py`, per table, against real rows |
| Composite foreign keys reject cross-owner references | The catalog checks every foreign key's shape. Behaviourally, an evidence grant across owners fails its foreign key |
| A worker can't cite another owner's evidence | `test_a_report_cannot_cite_another_owners_evidence` |
| Scheduler functions return only scheduling fields | `test_scheduler.py`, for every definer function |
| Catalog check over tables, unique indexes, roles and definer functions | `test_catalog.py`, `test_roles.py` and `test_scheduler.py` |
| Views use `security_invoker` | `test_views_run_with_the_callers_rights` |

**Deviations and decisions:**
- **The table suite runs as the migrator.** It owns the tables and holds every privilege, so row security is the only thing in the way, and every operation can be tried on every table. The runtime's narrower grants are checked separately: by the catalog, and by each table's own tests.
- **`capacity_slots` has an `owner_id` column.** It records the bound attempt's owner. T3.8's record says the table has no owner column, which was wrong. The table stays exempt from row security because it is installation-wide, and the runtime has no grant on it (T3.8's test). The scheduler's slot functions return only IDs and counts.
- **The tenant table list is written out in the test,** so a new table fails the suite until its rows come out of a full investigation and it is added there.

## 5. Validate implementation

**Planted faults.** Mutation testing can't reach the schema, so 16 faults were planted one at a time, each through a temporary migration. The table below lists the checks that failed for each.

| Fault | Caught by |
|---|---|
| A policy that lets every row through | the policy check; reads, no-owner reads, changes |
| A policy that accepts any write | the policy check; adding a row for another owner |
| Row security not forced on the table's owner | the table check; all five table operations |
| Row security disabled | the table check; all five table operations |
| A second, open policy | the table and policy checks; all five table operations |
| A policy for one role only | the policy check; reads, adds and give-aways (as the migrator) |
| A foreign key without the owner, onto a new unique index | the foreign key and unique key checks |
| A table that no longer references `owners` | the foreign key check |
| `TRUNCATE` granted to the runtime | the runtime grant check |
| A column `REFERENCES` grant | the runtime grant check |
| A table granted to `PUBLIC` | the `PUBLIC` check |
| A definer function outside the set | the definer check |
| A table in another schema | the schema check |
| A view without `security_invoker` | the view check |
| `current_owner_id()` reading another setting | the owner function check, and every behavioural test |
| A table owned by the scheduler | couldn't be planted |

The last one couldn't be planted: the migrator can't give a table to the scheduler, and the scheduler can't create one, because neither holds `CREATE` on the schema for it. The check stays, against a change made by a superuser.

**Other finding:** `capacity_slots` carries `owner_id`, contrary to T3.8's record. See §3.

## 6. Test

- `make check` passes offline with 1431 unit tests (unchanged), and 1 skipped because the network test only runs in CI.
- `make test-integration` passes with 378 tests. Of these, 66 are new:
  - 7 catalog checks;
  - 1 scheduler check (the scheduler owns no tables), and the definer check widened to every definer function;
  - 58 cross-owner tests: 5 operations on each of the 11 tenant tables, the listing check, the evidence grant and the citation.

**Limits:**
- **Tables from later tasks aren't here yet:** `tool_calls`, `investigation_tool_quota`, `tool_evidence` and `report_assessments`. The listing test makes each one fail the suite until it is added.
- **The catalog can't see application code.** That every worker write runs under the claimed owner is checked by the tests of each write path. The owner can't come from model output, since no contract carries one.
